The study prepares only after a person invokes **Prepare Speech** or initiates Voice Capture. The first mic permission grant is also a warmup opportunity. During normal capture load coalesces with the microphone buffer, so model work does not delay the **Listening** state. The recognizer retains at most one prepared portable pack for 60 seconds, releases on idle expiry, explicit cancellation or idle sleep notification, and uses a separate decoder state per capture. The operating system retains or evicts any compiled specialization. The study app is about 1.2 GiB and includes both model packs plus the frozen Swift runtime. A production build would deliver one pack. A measured cache-directory size reached 3.6 GB after sweeping eight configurations, then fell to a fraction of that. This is the study-identity cache after testing variants under disk pressure. It does not size a single production pack. A fixed asset URL reduces avoidable misses. An update or a sleep cycle can still trigger reinitialization. ### Compute trade-off

Fluid CPU-only loaded first in 3.47 s in the earlier profile, versus 16.85 s with CPU+ANE. For the matched 168-clip parity check, CPU produced exactly the same transcript for 157 clips. The others included a Portuguese fragment with unsupported English words and added English context in an adjacent meeting turn. Some mixed-word substitutions improved. Across the held speech, CPU WER was 21.69% PT, 14.26% EN, and 8.89% mixed. Its warmed short-PT median was 145 ms, versus 40 ms with CPU+ANE. CPU+GPU used about a 1 GB process footprint on tested runs and had 1.84 s first inference for Fluid on the mixed fixture. All-units first load was 20.86 s for Fluid, with greater observed footprint than CPU+ANE. Keep **CPU+ANE** for this pilot. CPU is a credible separate deployment option if it passes a larger independent critical-error review. Avoid switching compute config invisibly mid-capture. Fluid’s 168-clip process reported **681 MB RSS**, roughly **77 MB peak physical footprint** and **6.77 s user + 3.06 s sys CPU** for that batch. File-backed mappings and accessible working set contribute differently to RSS and footprint. Apple’s helper-process footprint is outside the app’s counters. In the Fluid 25-decode trial the estimated active app footprint rose to about 64 MB, leveled out by the last few repeats, and was 11.3 MB after expiry. These runs exercised cleanup and bounded retention. They are not proof of long-running leak freedom. Neural Engine residency and driver counters could not be reliably apportioned. macOS declined Power Profiler on this host and `powermetrics` requires privileges. Joules, thermal effect under real daily use, and a lower-memory Mac are unverified. [Batch resource output](results/held-fluid.resources) · [Power Profiler result](results/power-profiler.txt)

## Recording boundaries and native UI

The already authorized, metadata-only Round 1 probe ran 12 more times on this Mac. The built-in microphone delivered 4,800-frame buffers at 48 kHz. That is one 100 ms block. The first physical buffer was **4.04 s** from a fresh probe launch. Its engine start call took **3.93 s**. The other eleven arrived around **173 ms median**, spanning **169–177 ms**. This real input control informed the six-second startup watchdog. The signed study starts its **Listening** state only after the tap receives its first buffer. It retains the full first frame and never opens hot before explicit activation. [Hardware trace](results/earlier-probe-hardware.jsonl)

The 120 ms Finish tail can include approximately one additional hardware block on this route, with a visible **Finishing recording** cue while the microphone remains on. The deterministic fixture injects its final sound 40 ms after Finish and verifies it reaches recognition, then checks input release. This validates the state and buffer boundary. It does not establish an acoustic first/last-syllable improvement in the final build. Test actual quiet speech and release timing before shipping. Clips below one second get only a trailing zero pad for the portable runtime. A short click or digital silence fails the activity gate. Low-level ambient rejection and soft human speech remain real-world checks. No silence-based auto stop.

## Reliability and offline

The final signed optimized app passed 14 assertion groups with 43 matched fixture input starts and stops. Coverage includes boundary readiness, 120 ms tail, duplicated Finish and Keep, injected SQLite write rejection, Retry, recovery of failed automatic Keep across reopening, durability across reopening the actual SQLite store, the separate scratch, editing and guarded Undo, silent and click-only rejection, route/sleep handler interruption, timeout, a deliberately noncooperative recognizer returning after cancel and retry, pending review-text recovery, 30 repeated cancellations and explicit study reset. The test also runs Apple recognition on a bundled synthetic fixture. The workflow probes exercise all three recognizers and actual writes. Unexpected physical process loss before transcript creation cannot recover audio. Force-restart tests exercise the same recovery storage by reopening the repository. [Automated run](results/validation.txt)

**Offline verified.** The signed app ran on this Mac after the Apple language setup with Wi‑Fi powered off. macOS reported no active IPv4 or IPv6 network state, and an unrelated public test endpoint reachable before the disconnect was inaccessible during the test. Each candidate transcribed both the bundled EN and PT fixtures without a live connection, preserving the negation. Network was restored after the run. This demonstrates initialized local inference in the tested signed build. The native app does not request outbound network access. Production constraints on TCC, offline setup after upgrades, and potentially broader platform cases are in the integration gates. [Disconnected trace](results/disconnected-network.txt) · [Entitlements and identity](results/environment-and-signing.txt)

Local runtime logging in the used batch path contains setup and execution metadata. Transcript output in the benchmark commands is restricted to research fixtures. Studio evaluation files stay in the isolated container and are opt-in. Default audio retention is bounded RAM while an attempt can be recovered. Only the explicit evaluation export writes audio. None of the benchmark files in the app are private or unrelated user data. [Privacy and release integration](INTEGRATION.md)
