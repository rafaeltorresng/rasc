# Production integration proposal

The signed study is the pilot. Keep production gated on human workflow value, boundary fidelity, and predictable microphone permission after a release update. Limit the first production scope to one engine, one opt-in toggle shortcut, and standard Rasc notes. The best supported starting point is the pinned Fluid Speech Pro Core ML pack in verbatim mode. Keep Ultra as a study comparator while validating the short Portuguese omissions.

## Model and asset policy

- Pin one licensed model revision, runtime revision, tokenizer and Core ML configuration. Evaluate an upstream port against the same PCM, including sub-second padding, before replacing the author fork. Review the code path used by verbatim batch decoding and its transitive dependencies. Supply attribution and a license for the model and conversion. [Fluid Speech Pro conversion](https://huggingface.co/FluidVoice-Labs/fluid-speech-pro-coreml/tree/3b9d38a93d606f84011e5a0a669b7ea146375a22)
- Prefer a stable, versioned asset location for Core ML specialization, with buckets keyed by engine, exact version and content hash. Allow macOS to evict its optimization cache. Prepare only after a person enables or uses voice. Treat first initialization and macOS cache eviction as ordinary, recoverable states. Avoid running anything model-related on normal app launch. [Apple Core ML model lifecycle](https://developer.apple.com/videos/play/wwdc2023/10049/)
- The study bundles both signed packs and never invokes a third-party downloader. Shipping can bundle a single reviewed pack or use an explicit separate import with no outgoing network in the capture app. Choose the smallest delivery path after measuring download, storage and update behavior. For separate package delivery, verify a signed manifest and each asset hash, bound size and entries, stage privately, reject symlinks and path traversal, and move a complete pack atomically. Keep the last verified pack until the replacement loads. No verification failure should trigger an inference upload.
- Do not use private note text as vocabulary hints or automatically bias the model with each test answer. Any production vocabulary feature needs distinct human evidence and a privacy/logging review of the exact runtime. No need for an agent, network fallback, or arbitrary model import UI.

## Privacy and persistence

The study bundle requests only App Sandbox and Audio Input. Its microphone prompt has a narrow usage description. Apple SpeechAnalyzer language downloads are opt-in through the OS, with future offline behavior verified independently. The portable path reads packaged artifacts. No transport API receives speech, text or evaluation output.

Audio is bounded to 90 seconds in RAM. A capture that requires human recovery retains audio only while retry remains possible. Keep or Discard releases it. Restart can recover transcript text that was already staged, including saved review edits. It cannot recover audio from an abrupt termination before transcription. Study export requires a separate action and is removable from its own container. Remove eval storage and controls from the shipping path. Do not market logical deletion as physical secure erasure of SQLite blocks or backups.

Durable Keep produces an ordinary note only after the repository commits. Use guarded Undo that targets the exact receipt snapshot. An already edited note should never be reverted by Undo Capture. Existing drafts, inline edits and searches will need end-to-end app integration tests.

## Signing and update prerequisites

Apple documents that macOS stores the app’s designated requirement as microphone authorization identity. Ad-hoc requirements are tied to the code version. The Round 2 local Sparkle event trace confirmed this on the actual distribution pattern. A fixed bundle identifier and install path alone did not preserve permission. The comparison with unchanged code at a relocated or reinstalled path did preserve it. [Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements) · [Round 2 Sparkle trace](../Round2/results/sparkle-events.txt) · [Sparkle sandboxing](https://sparkle-project.org/documentation/sandboxing/)

For continuity across releases, use a stable requirement that verifies the real publisher. Developer ID Application signing is the practical option for a directly distributed app and Sparkle chain. Use the same Team ID and bundle identifier on two release-equivalent fixtures, check that each build satisfies the other build’s requirement, then grant the first and use a genuine signed Sparkle update. Test deny, reauthorize, reinstall, relocation and the ad-hoc-to-Developer-ID transition using a disposable account. Notarization addresses distribution/Gatekeeper. It does not itself give TCC an identity. No Developer ID Application identity is available in the local signing keychains used here. Obtaining one, enabling notarization and changing production signing are release-policy decisions.

Under current ad-hoc distribution, the pilot checks AVFoundation authorization each time a person explicitly starts and routes denials to System Settings. Be explicit if an update makes macOS ask again. A predictable prompt is a useful recovery route and still needs a ship decision. There is no designed TCC bypass, weak custom requirement, protected database modification, or broader entitlement.

## Go/No-Go gates

1. **Human value.** Compare natural usage against typing and Apple Dictation. Time correct, committed thought plus return to prior activity, including corrections. Demonstrate a meaningful time or effort advantage for longer thoughts, occupied hands or accessibility use. Establish that the advantage survives fully cold attempts and setup friction.
2. **Fidelity.** With consent, record independently held-out spontaneous PT-BR, English and mixed speech, with speakers disjoint from development. Include physical shortcut boundaries, soft voices, quiet/noisy rooms, names, tech identifiers, corrections and pauses. Require ≥99% first/last word preservation when paired with physical keyboard readiness trials and zero meaning-changing critical errors in the staged release test before default automatic Keep. Report sample size, ambiguity and observed omissions. A review-first pilot can continue even if automatic Keep fails.
3. **Latency.** Target prepared mic readiness ≤300 ms at p95, visible short-capture acknowledgment ≤100 ms, and finish-to-durable Keep ≤1 s at p95. Test cold, restart, after cache eviction, idle, sleep, update and lower-memory Apple Silicon alongside active work. Treat repeated multi-second delay in normal use as a blocker. Compare selected compute config against the development clips without changing held-out scoring.
4. **Correctness and accessibility.** Confirm no noise-only note, lost draft, duplicate, premature Kept receipt, stale result or lost recoverable text. Repeat fast cancellation with physical shortcuts, interrupted saves, power/sleep transitions and device changes. Verify VoiceOver, Full Keyboard Access, Reduce Motion, light/dark, fullscreen, Spaces, Stage Manager and multi-display coordinates on real configurations.
5. **Release safety.** Verify offline after setup and following the signed updater, no unreviewed speech egress, artifact integrity, bounded cache storage, and TCC continuity or explicitly approved reauthorization. Validate an actual release-style app build, never infer these results from the lab alone.
